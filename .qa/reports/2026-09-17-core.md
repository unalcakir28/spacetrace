## S1 — A deep directory tree aborted the process; the agent died with it

### What it was

Reproduced three times independently. 209 levels completed, **210 aborted**:

```
thread 'spacetrace-walk-0' has overflowed its stack
fatal runtime error: stack overflow, aborting
exit=134                       # SIGABRT
```

Against a running agent, a root containing such a tree killed the service:
`POST /scans` returned 202, then the pid left `ps`, the port stopped listening,
`curl` got connection refused, and **no snapshot was written**. The scheduler and
the HTTP API went with it.

### Root cause

`walk()` recurses once per directory level on the rayon pool, and `walk_pool()`
built that pool without `.stack_size()`, so workers got the ordinary default
thread stack. Confirmed before touching anything: the same 300-level tree that
aborted scanned in 21 ms under `RUST_MIN_STACK=67108864`.

### The fix

`crates/scan-core/src/scan.rs`:

- `WALK_STACK_BYTES` (16 MiB) given to the walk pool. The measurement above is
  what says this works.
- `MAX_WALK_DEPTH` (1024) as a hard bound that is *not* the caller's
  `max_depth`. Past it a directory is recorded through `note_error` — the same
  path an unreadable directory takes — and the scan carries on. This is the part
  that makes the stack no longer the thing that decides.

### Verification

| | |
|---|---|
| `scan` on a 300-level tree | **exit 0**, 301 dirs, 33 ms (was exit 134) |
| the agent on the same tree | **stays up**; snapshot #1 written, 303 dirs, 0 errors, 25 ms |
| a 3000-level tree | exit 0, and the failure is **named**: `1 paths could not be read … File name too long (os error 63)` with the full path |

The third row is the one worth keeping: past what the OS can name, the scan
reports the exact path and reason instead of stopping quietly. macOS reaches
`ENAMETOOLONG` around 475 levels, so on this platform the new depth bound is
never what stops the walk — on Linux, where `PATH_MAX` is four times larger, it
will be.

**Regression test:** `a_deeply_nested_tree_does_not_abort_the_process` in
`crates/scan-core/tests/scan.rs`, 400 levels, asserting zero errors and a
complete count. The red half was demonstrated against the binary (exit 134,
three times) rather than through the harness, because the pre-fix failure aborts
the whole test process instead of failing an assertion.

### One claim in the first draft of this report was wrong

It said the agent's configuration offers no depth limit. It does:
`roots[].depth` exists in `RootConfig`, maps to `ScanOptions::max_depth`, and is
in the configuration reference table in `docs/AGENT.md`. Only the example config
block omits it, which is what was read. The severity does not change — the
default is unlimited and nothing warned — but "no mitigation existed" was false.

## S3 — `/health` and its documentation disagreed

```json
{"status":"ok","version":"0.7.0","commit":"805e0ac","channel":"dev"}
```

`docs/AGENT.md` said, twice, that the body is `status` and `version` only.

**Fixed in the document, not the endpoint**, and that is a deliberate choice.
The code carries an explicit reason for `commit` — `/health` needs no
credential, so it is the one thing an operator can read off a machine they are
only half sure about, and every continuous build shares a version number. The
existing test `health_needs_no_token_and_leaks_nothing` encodes the invariant
that actually matters and still passes: no roots, no hostname, nothing about
what the machine holds. `commit` and `channel` describe the build, not the box,
so the document's own stated concern was never violated — its field list had
simply gone stale.

The test now **pins the exact field set**, so the next addition has to be
deliberate and update both sides rather than being discovered with `curl`.

## Withdrawn — the CLI accepting a file as a scan root

Reported as a divergence: the CLI scans a file and exits 0, the agent answers
400, and the agent's own test calls it a client error.

**It is not a bug.** `scanning_a_single_file_yields_a_one_node_tree` in
`crates/scan-core/tests/scan.rs` specifies the library's behaviour, and the
attempted fix broke it. Read properly, the two layers are deliberately
different: the library is permissive like `du`, and the agent is strict because
a *scheduled* scan of a single file is meaningless. The finding came from not
checking whether a passing test already guarded the behaviour, which is the one
question that should have been asked before writing it up.

surface. `render.rs:47` deliberately writes `## Unreleased` into the generated

# Verdict: **GO WITH RISK**

The S1 is fixed, verified three ways, and covered by a regression test. What
keeps this off a clean GO is that the fix has **only been exercised on macOS**,
and the defect was platform-dependent by nature: the stack size that caused it
is a per-platform default, and `MAX_WALK_DEPTH` cannot even be reached on this
platform because `PATH_MAX` stops the walk first. On Windows — the next machine
in use, and the one with the smallest default stack — none of this has run.

**Re-run CORE-024 on Windows before calling it closed.** Everything else found
was documentation drift or a finding that did not survive scrutiny.
